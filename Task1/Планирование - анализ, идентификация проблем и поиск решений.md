# Планирование: анализ, идентификация проблем и поиск решений

Кейс: компания «Александрит» (производство ювелирных украшений, онлайн-магазин + CRM + MES).

> Примечание: анализ построен по тексту кейса и C4-схеме (контейнерный уровень). Где вывод — гипотеза, а не факт, так и указано. Гипотезы нужно проверить метриками (см. инициативу И-1).

---

## 0. Что видно на схеме (ключевые наблюдения)

1. **MES API (C#) — один контейнер, который делает всё сразу**: принимает запросы внешних API-клиентов (стрелка «API user → MES API» идёт напрямую), раздаёт заказы операторам, показывает список заказов (дашборд) и **считает цену** (2–30 минут). Всё это в одном процессе, на одном EC2, с одной БД.
2. **У CRM нет своей базы.** CRM API пишет прямо в **Shop DB**, то есть CRM и онлайн-магазин (B2C) делят одну БД. Нагрузка продавцов и клиентов магазина конкурирует за неё.
3. **Данные заказа лежат в двух БД** (Shop DB — «с точки зрения клиента», MES db — «с точки зрения производства») и синхронизируются только сообщениями через очередь.
4. **Одна очередь RabbitMQ** («has several topics») связывает CRM API и MES API. Отдельных очередей по типам нагрузки (лёгкие/тяжёлые модели, внешние/внутренние заказы) нет.
5. **Одно хранилище 3D-файлов (S3)**, в которое пишут Shop API и CRM API, а читает MES API. Файл загружается **через Shop API** (стрелка «uploads files»), то есть тяжёлые файлы идут через бэкенд магазина.
6. **На схеме нет**: API Gateway, балансировщика, кэша, реплик БД, мониторинга, сервиса уведомлений, интеграции с транспортной компанией (хотя статус CLOSED приходит от неё).
7. **Заказ от внешнего API-клиента** попадает сначала в MES API → MES db, и только потом сообщением в CRM API → Shop DB. Это самый длинный и самый хрупкий путь в системе.

---

## 1. Что происходит (коротко)

- Заказов становится на 100 больше каждый месяц, а после открытия внешнего API нагрузка резко выросла.
- Производство справляется (может вынести рост в 2 раза), значит **узкое место не в цехе, а в ПО и процессах**.
- Заказы теряются или задерживаются на пути «онлайн-магазин / API → MES (расчёт цены) → RabbitMQ → CRM → MES (производство)».
- Дашборд MES тормозит, операторы теряют деньги (кто первый взял заказ, тот получил оплату).
- Из-за этого уже потеряны крупные B2B-контракты.

## 2. Список проблем

### 2.1. Существующие проблемы

| № | Проблема | Почему это проблема | Связь с симптомом |
|---|----------|---------------------|-------------------|
| П-1 | **Расчёт стоимости (2–30 минут) выполняется внутри MES API**, в том же контейнере, что и приём запросов API-клиентов и дашборд операторов | Тяжёлые расчёты забирают процессор и потоки у всего остального. Одна тяжёлая 3D-модель может надолго занять обработчик, остальные заказы ждут (эффект «очереди в магазине за человеком с тележкой») | Просроченные заказы, жалобы B2C и API-клиентов, тормоза дашборда |
| П-2 | **Единственный экземпляр каждого приложения** (по одному EC2) | Нет масштабирования, любой сбой или перегрузка = простой всей функции | Рост нагрузки сразу бьёт по всем |
| П-3 | **Одна БД на запись и чтение** (один инстанс) | Дашборд, расчёты и записи заказов конкурируют за одну базу | Тормозящий дашборд MES, замедление всей системы |
| П-4 | **Дашборд MES медленный, несмотря на фильтр и пагинацию** | Значит, причина глубже. По схеме главный подозреваемый: список заказов отдаёт тот же MES API, который занят расчётами цены и запросами внешних клиентов, и всё это ходит в одну MES db. Дополнительно (гипотеза): медленные запросы, нет индексов, пагинация через OFFSET, сортировка по «новизне» без индекса | Жалобы операторов, потеря их заработка |
| П-5 | **Ненадёжная интеграция CRM ↔ MES через RabbitMQ** | Не описано: подтверждения (ack), повторные попытки, очередь «мёртвых» сообщений (DLQ), идемпотентность, контроль потерь. Если сообщение потерялось, заказ «зависает» навсегда | «Не получили свои заказы» |
| П-6 | **Нет наблюдаемости** (метрики, логи, трассировка, алерты) — гипотеза, в кейсе не упомянуто | О проблемах узнаём от клиентов, а не от системы. Не видно, где именно застревают заказы | Месяцы поиска причин, потеря контрактов |
| П-7 | **Публичный API открыт без явной защиты от перегрузки** (rate limit, квоты, приоритеты) | Внешние продавцы создают заказы через тот же путь (MES → очередь → CRM), что и свои клиенты. Один «шумный» клиент может задавить остальных | «Завалило заказами», ухудшение для B2C |
| П-8 | **Ручное E2E-тестирование и ручные выкаты** (release и prod) | Релизы медленные, растут задержки (раньше до месяца, теперь больше). Баг high/highest блокирует весь релиз. Исправления проблем доезжают до клиентов поздно | Медленная реакция на проблемы |
| П-9 | **Мало автоматических тестов** (на dev только unit-тесты) | Нет интеграционных и нагрузочных тестов, регрессии находит человек руками | Задержки релизов |

### 2.2. Потенциальные проблемы (ещё не случились, но случатся)

| № | Проблема | Почему важно |
|---|----------|--------------|
| П-10 | **Линейный рост +100 заказов/мес** | Каждая найденная «узкая точка» через несколько месяцев снова станет проблемой. Нужна проверка запаса прочности (нагрузочные тесты) |
| П-11 | **Состояние заказа меняют три системы** (магазин, MES, CRM) | Нет единого владельца статуса. Возможны рассинхронизация и «застрявшие» заказы без таймаутов и контроля SLA |
| П-12 | **Гонка операторов за заказ** | При росте нагрузки два оператора могут взять один заказ (нет оптимистичной блокировки) — гипотеза |
| П-13 | **Единая точка отказа в БД и очереди** | Падение базы или RabbitMQ останавливает все три приложения. Про бэкапы, отказоустойчивость очереди и план восстановления в кейсе ничего нет |
| П-14 | **Нет Infrastructure as Code, ручное управление EC2** | Невоспроизводимые окружения, медленное масштабирование, зависимость от одного DevOps |
| П-15 | **Риски по людям (bus factor)**: один C#-разработчик (а MES на C#, куплен вместе с исходниками), один DevOps, один QA | Уход или болезнь любого из них блокирует целое направление |
| П-16 | **Разнородный стек** (Java, C#, Vue, React) при команде из 8 человек | Дорогая поддержка, мало взаимозаменяемости |
| П-17 | **Нет прозрачности для клиентов API** (статус заказа, вебхуки, ожидаемое время расчёта) | Клиенты пишут в поддержку вместо того, чтобы сами видеть статус |
| П-18 | **Нет SLA и ожиданий по времени** в самой системе (напр. «расчёт не дольше N минут») | Нечем измерять качество и нечего показывать бизнесу |
| П-19 | **CRM и онлайн-магазин делят одну БД (Shop DB)**: CRM API пишет прямо в неё | Нагрузка продавцов и клиентов B2C конкурирует за одну базу. Изменение схемы для одной системы ломает другую. Падение базы останавливает и магазин, и CRM |
| П-20 | **Данные заказа лежат в двух БД** (Shop DB и MES db), синхронизация только сообщениями | Любая потеря или задержка сообщения даёт расхождение статусов. Нет сверки, кто прав |
| П-21 | **Внешние API-клиенты ходят прямо в MES API**, в тот же сервис, что обслуживает операторов | Всплеск запросов от одного партнёра замедляет работу операторов и расчёты. Нет изоляции, квот и приоритетов |
| П-22 | **Одна очередь RabbitMQ с несколькими topics для всех типов сообщений** | Тяжёлые и срочные сообщения идут по одному каналу. Нет раздельных очередей по приоритету и источнику (свои/внешние заказы) |
| П-23 | **Загрузка 3D-файлов идёт через Shop API** | Тяжёлые файлы нагружают бэкенд магазина. Надёжнее загружать напрямую в S3 по временной ссылке (pre-signed URL) |
| П-24 | **Подтверждение заказа продавцом вручную в CRM** (статус MANUFACTURING_APPROVED) — гипотеза | Если продавцов мало или у них нет приоритетов и напоминаний, заказы лежат без движения. Часть «месяцев ожидания» может быть именно здесь, а не в ПО |

## 4. Приоритеты и ход рассуждений

### 4.1. Как расставлял приоритеты

Критерии (по убыванию важности):
1. **Прямая связь с потерей денег и клиентов** (просроченные заказы, потерянные заказы, B2B-контракты).
2. **Скорость эффекта**: что быстро и дёшево снижает боль.
3. **«Сначала узнать причину»**: нельзя чинить вслепую, поэтому наблюдаемость идёт первой.
4. **Зависимости**: без одного нельзя сделать другое (например, автотесты нужны до серьёзных изменений в очередях).
5. **Риск**: что случится, если не делать.

### 4.2. Порядок

**Волна 0 — «остановить кровотечение» (недели 1–4)**
- И-1 Наблюдаемость и алерты
- И-11 Таймауты и правила статусов (минимум: алерт на «застрявшие»)
- И-15 Контроль подтверждения заказов продавцами (дёшево и может сразу сдвинуть часть заказов)
- И-12 Коммуникация с клиентами (параллельно, силами продакта)
- Ручная сверка текущих «зависших» заказов, чтобы вернуть заказы и доверие

**Волна 1 — «чинить главные причины» (месяцы 1–3)**
- И-2 Надёжные сообщения (ретраи, DLQ, идемпотентность, Outbox)
- И-3 Разгрузка расчёта стоимости (отдельные очереди и пул воркеров)
- И-5 Оптимизация БД и дашборда MES
- И-4 Минимум 2 экземпляра приложений

**Волна 2 — «защититься и ускорить команду» (месяцы 2–5)**
- И-6 API Gateway, квоты, асинхронный API
- И-7 Автотесты (стартуют с волны 0 на критическом пути)
- И-8 CI/CD
- И-9 IaC и бэкапы
- И-14 Прямая загрузка 3D-файлов в S3

**Волна 3 — «закрепить» (месяцы 3–6)**
- И-13 Развязка данных CRM и магазина
- И-10 Найм (запрос стартует сразу, потому что найм долгий)
- Нагрузочное тестирование и план ёмкости

### 4.3. Какой вижу целевую архитектуру через полгода

В словах простым языком:

- **Вход.** Внешние продавцы ходят через **API Gateway** (лимиты, квоты, ключи по клиентам) в отдельный внешний API, а не напрямую в MES API. Ответ быстрый: «заказ принят, вот его номер». Статус можно смотреть или получить вебхуком.
- **Приложения.** Магазин, CRM и MES API работают минимум в **двух экземплярах** за балансировщиком. Выкат без простоя.
- **Расчёт стоимости.** Вынесен из MES API в отдельный **сервис с пулом воркеров** и **двумя очередями** (быстрые и тяжёлые модели) с ограничением времени. Воркеров можно добавлять без переделок. Лёгкие заказы больше не ждут тяжёлые, а MES API остаётся быстрым для операторов.
- **Файлы.** 3D-модели грузятся напрямую в S3, бэкенд магазина не тащит тяжёлый трафик.
- **Очередь.** RabbitMQ в отказоустойчивой конфигурации; сообщения подтверждаются, есть повторные попытки, DLQ, идемпотентность. Заказ не теряется молча, а при проблеме приходит алерт.
- **БД.** MES db: основная база на запись + **реплика на чтение** для дашборда и отчётов, правильные индексы, кэш для первой страницы MES. Операторы видят свежие заказы за секунды, список обновляется по событиям. CRM и магазин развязаны хотя бы по схемам и правам (в идеале отдельная БД CRM), чтобы не мешать друг другу.
- **Наблюдаемость.** Единый дашборд «здоровья» заказов: сколько заказов в каждом статусе, самый старый заказ, глубина очередей, время расчёта. Алерты уходят команде раньше, чем позвонит клиент.
- **Процессы.** Автотесты критического пути и нагрузочные тесты, автодеплой на release, выкат на prod одной кнопкой с откатом, инфраструктура описана кодом, бэкапы проверяются.
- **Команда.** Есть второй человек на C#/MES и второй на DevOps, QA занимается автоматизацией.

Что **намеренно не делаю** за полгода: не разбиваю систему на десятки микросервисов и не переписываю MES (куплен с исходниками, работает). Это дорого и не решает причины проблем. Решаем только то, что бьёт по клиентам.

### 4.4. Если можно выбрать только три пункта

**1. И-1 Наблюдаемость и алерты (с таймаутами по статусам, И-11).**
Почему: это дёшево, быстро (2–3 недели) и даёт то, чего сейчас нет, — **понимание, где именно теряются и застревают заказы**. Сегодня все выводы — гипотезы. Без этого остальные два пункта можно сделать «не туда». Алерты сразу сокращают время реакции с «месяцы, пока клиент пожалуется» до «минуты».

**2. И-2 + И-3 Надёжная очередь и разгрузка расчёта стоимости (ядро главной проблемы).**
Почему: именно сюда, по описанию и схеме, уходят заказы — долгий расчёт (до 30 минут) выполняется прямо внутри MES API рядом с дашбордом и запросами внешних клиентов, а ненадёжные сообщения теряют заказы. Это прямо бьёт по B2C и по потерянным API-контрактам. Производство держит 2× рост, значит, как только заказы будут нормально доходить, бизнес сразу получит эффект. Сюда входят раздельные очереди, масштабируемые воркеры, ретраи и DLQ, идемпотентность.

**3. И-5 Оптимизация БД MES и дашборда (с оптимистичной блокировкой при взятии заказа) и по пути минимум 2 экземпляра приложений (И-4).**
Почему: прямая потеря денег у операторов и операторской мотивации. Фильтры и пагинацию уже пробовали, и это не помогло, то есть причина глубже. Часть эффекта даст пункт 2 (расчёт уйдёт из MES API), остальное — запросы, индексы и единая MES db. Это относительно локальная задача (1–2 месяца), эффект заметен сразу. Реплика на чтение заодно снимает нагрузку с единственной БД.

**Почему не выбрал остальное в «тройку»:**
- **Автотесты и CI/CD (И-7, И-8)** очень важны и стратегически, и идут параллельно силами QA и DevOps (они не блокируют разработчиков по пунктам 1–3). Но они **не убирают текущую боль клиентов** напрямую, а ускоряют будущие исправления. Поэтому в «тройку» не попали, но стартуют сразу.
- **API Gateway (И-6)** — важен, но пока заказы теряются внутри, шлюз перед сломанной обработкой не поможет. Станет следующим шагом.
- **Найм (И-10)** — решение длинное по времени. Запрос на найм второго C#-разработчика и QA-автоматизатора нужно начать сразу, но это не «пункт инженерного плана», а условие, чтобы план был выполнимым.
- **IaC (И-9)** и **единый стек** — полезны, но не срочны по сравнению с потерей клиентов.

### 4.5. Как проверим, что стало лучше (метрики успеха)

- Доля заказов, прошедших от SUBMITTED до PRICE_CALCULATED за ≤ 5 минут (цель: 95%+ для лёгких моделей).
- Количество «застрявших» заказов (старше порога) — стремится к нулю.
- Время загрузки первой страницы MES (цель: до 1–2 секунд).
- Количество жалоб на просроченные заказы (B2C и API) в неделю.
- Время от готового исправления до выката на prod (цель: дни, а не месяцы).
