# Архитектурное решение по трейсингу

Технический документ. Проект: «Александрит» (онлайн-магазин, CRM, MES, внешний API).

Что такое трейсинг, простыми словами: это «история пути» одного заказа. Каждый сервис, через который проходит заказ, оставляет отметку: когда получил, что сделал, сколько это заняло, чем закончилось. Все отметки собираются в одну цепочку, и по номеру заказа можно увидеть весь его путь и место, где он остановился.

## 1. Анализ системы: что нужно покрыть трейсингом

### 1.1. Что видно на схеме C4 и допущения

- Заказ проходит через три приложения и две базы: Shop API → Shop DB, CRM API → (та же) Shop DB, MES API → MES db. Между CRM и MES связь только через одну очередь RabbitMQ.
- **Допущение (проверить по коду на первой неделе внедрения).** На схеме у Shop API нет связи с очередью. Значит, заказ из магазина попадает в MES так: Shop API сохраняет заказ в Shop DB, CRM API забирает его из общей БД и публикует в очередь для MES. Если это не так, точка T2 ниже изменится, остальное остаётся.
- Внешний API-клиент заходит прямо в MES API (расчёт цены), потом заказ сообщением уходит в CRM API и Shop DB.
- На схеме нет транспортной компании, хотя статус CLOSED приходит от неё. Эту интеграцию мы не видим и в трейсинг пока не включаем.

### 1.2. Места, где заказ может «сломаться» или зависнуть

Номера T1–T8 стоят на диаграмме (вариант 1).

| № | Где | Что может пойти не так | Как это выглядит для бизнеса | Что трейсинг покажет |
|---|-----|------------------------|------------------------------|----------------------|
| **T1** | **Shop API** (+ Internet Shop, S3, Shop DB): INITIATED → FILE_UPLOADED → SUBMITTED | Файл не загрузился или загрузился не полностью, заказ сохранён без файла, ошибка записи в Shop DB, потерянный запрос при перегрузке | Клиент нажал «Сделать заказ», но заказа нет или он «пустой» | Спаны загрузки файла, записи в БД, ошибки, время каждого шага |
| **T2** | **CRM API ↔ Shop DB** (передача заказа из магазина в производство) | Заказ SUBMITTED лежит в Shop DB, но CRM API его не подхватил (опрос БД упал, фильтр пропустил, конфликт блокировок) и не опубликовал сообщение | Заказ «пропал»: он есть в магазине, а производство о нём не знает | Есть спан SUBMITTED, но **нет следующего спана** публикации в очередь. Алерт по отсутствию (раздел 4.5) |
| **T3** | **RabbitMQ** (Messages Queue) | Сообщение не опубликовано, застряло в очереди, ушло в DLQ, обработано дважды, потеряно между повторами | Заказ стоит часами или днями «в воздухе»; пользователи API «не получили заказ» | Время ожидания в очереди (от публикации до получения), число повторов, признак DLQ, идентификатор сообщения |
| **T4** | **MES API**: приём заказа, чтение 3D-файла из S3, расчёт цены (PRICE_CALCULATED) | Файл не читается, расчёт идёт 30 минут и дольше, таймаут, процесс упал во время расчёта, результат не отправлен обратно | Заказ «висит» в SUBMITTED; клиент ждёт цену | Спаны чтения файла и расчёта, размер модели, длительность, исход (ok / error / timeout), отправка результата |
| **T5** | **Вход API-клиента → MES API** | Запрос внешнего клиента отклонён или потерян при перегрузке, ответ клиенту не вернулся, заказ создан в MES db, но сообщение в CRM не ушло | Жалобы «не получили свои заказы» от внешних продавцов | Входящий запрос по клиенту, ответ, спан записи в MES db и публикации сообщения |
| **T6** | **CRM / CRM API**: приём цены и подтверждение заказа продавцом (MANUFACTURING_APPROVED) | Сообщение с ценой пришло, но не обработано; продавец долго не подтверждает (ручной шаг); подтверждение не дошло до MES | Заказ ждёт «подтверждения», хотя клиент уже готов | Спан получения сообщения, спан подтверждения и **время между ними** (ожидание человека), отправка в MES |
| **T7** | **MES API / MES**: назначение оператору, производство, упаковка, отправка (MANUFACTURING_STARTED … SHIPPED) | Два оператора берут один заказ, заказ не назначается, статус не обновился, сообщение об изменении статуса не дошло до CRM | Операторы теряют заработок, заказ «в работе» по данным MES и «ожидает» по данным CRM | Спаны смены статуса, время в каждом статусе, отправка событий в CRM |
| **T8** | **CRM API**: закрытие заказа (CLOSED) | Сообщение от транспортной компании не пришло или не обработано, заказ закрывается вручную и забывается | Заказ завершён физически, но «висит» в системе | Время от SHIPPED до CLOSED, ручное закрытие или автоматическое |

### 1.3. Какие системы покрываем трейсингом

| Компонент | Покрытие | Почему |
|-----------|----------|--------|
| Shop API | **Да** (Java agent) | Начало пути заказа (T1) |
| CRM API | **Да** (Java agent) | Передача, подтверждение, закрытие (T2, T6, T8) |
| MES API | **Да** (.NET SDK, исходники есть) | Расчёт цены, вход API-клиентов, производство (T4, T5, T7) |
| RabbitMQ | **Да, через заголовки сообщений** | Контекст трассировки передаётся внутри сообщения (T3). Сам брокер даёт метрики (задание 2) |
| Shop DB, MES db, S3 | **Да, как «вызовы» из сервисов** | Видим время и ошибки запросов и операций; внутрь баз трейсинг не ставим |
| Фронтенды (Shop, CRM, MES) | **Опционально, второй этап** (OTel Web SDK) | Дают «начало» пути в браузере. На старте не обязательны: заказ можно полноценно отследить с момента запроса к API |
| Транспортная компания, внешние API-клиенты | **Нет** (вне нашего контроля) | Принимаем входящий контекст, но не требуем его (раздел 6) |

## 2. Данные, которые должны попадать в трейсинг

### 2.1. Что записываем

**Идентификаторы и связь**
- `trace_id`, `span_id`, `parent_span_id` — стандартные идентификаторы цепочки.
- `order.id` — номер заказа (главный поисковый ключ).
- `order.source` — откуда заказ: `b2c` (магазин) или `api` (внешний клиент).
- `client.id` — идентификатор внешнего API-клиента (договорный, не личные данные).
- `user.role` и обезличенный `user.hash` — продавец, оператор, клиент (по хэшу, без имён).

**Состояние заказа**
- `order.status.from` и `order.status.to` — переход (например, `SUBMITTED → PRICE_CALCULATED`).
- Время начала, окончания и длительность шага.
- `order.step.owner` — кто на ходу: система или человек (продавец, оператор).

**Сервис и окружение**
- `service.name`, `service.version`, `deployment.environment` (dev / release / prod), `host.name`.

**Сообщения RabbitMQ**
- `messaging.destination` (обменник, очередь, ключ маршрутизации), `messaging.message_id`.
- Время публикации и время получения (из них считаем время ожидания в очереди).
- Номер попытки (`retry.attempt`), признак `dlq=true` и причина.

**Расчёт цены**
- `model.file_id`, `model.size_bytes`, `model.polygons`.
- `calc.duration_ms`, `calc.result` (ok / error / timeout).

**Запросы и базы**
- `http.method`, `http.route` (шаблон маршрута без ID), `http.status_code`.
- `db.system`, `db.operation`, длительность, число строк. Текст запроса — **без значений параметров**.

**Ошибки**
- `error.type`, краткое сообщение, стек (в обрезанном виде).

### 2.2. Чего в трейсинге быть не должно

- Имя, телефон, e-mail, адрес клиента, платёжные и банковские данные.
- Пароли, токены, заголовки `Authorization`, cookie.
- Тела запросов и ответов целиком, содержимое 3D-файлов.
- Цена и состав заказа в явном виде (если понадобится, только диапазон или признак).

Это закрепляется настройками Collector (раздел 6.2) и ревью атрибутов на внедрении.

## 3. Мотивация

### 3.1. Почему нужен трейсинг

- **Сейчас на вопрос «где мой заказ?» нет ответа.** Менеджер звонит разработчику, разработчик вручную смотрит в две базы и в очередь. Это часы или дни.
- **Метрики и логи показывают симптомы, но не путь заказа.** Задание 2 даст метрики («очередь растёт», «ошибок больше»). Но по метрике нельзя понять, какой конкретно заказ потерялся и где. Трейсинг связывает всё в одну историю заказа.
- **Заказ проходит через три приложения, две базы и очередь.** Сообщения могут теряться (по описанию задания), статусы меняют разные системы. Без сквозной цепочки такие проблемы не найти.
- **Заказ живёт неделями.** Жалоба приходит, когда прошёл месяц. Нужно уметь «перемотать» его историю назад.
- **Уже потеряны контракты.** Внешним клиентам нужно честно отвечать, где заказ и когда он будет готов.

### 3.2. Что это даст компании

| Кому | Что получает |
|------|--------------|
| **Поддержка и менеджеры по продажам** | Вводят номер заказа и сразу видят, где он стоит и сколько простаивает. Отвечают клиенту за минуты без помощи разработчиков |
| **Разработчики** | Находят причину сбоя по конкретному заказу: какой сервис, какой шаг, какая ошибка. Не тратят дни на ручное расследование |
| **Продакт и бизнес** | Видят, на каком шаге заказы теряют больше всего времени (расчёт, очередь, подтверждение продавцом, производство). Обоснованно выбирают, что чинить первым |
| **Операторы** | Видно, почему новый заказ не доходит до дашборда, и можно исправить причину |
| **Внешние клиенты API** | Получают прозрачные статусы и сроки (на основе тех же данных), доверие растёт |

### 3.3. Метрики, на которые повлияет внедрение

Значения — ориентиры; текущие цифры нужно замерить в первые 2–4 недели (в том числе вручную по жалобам) и затем зафиксировать целевые.

| № | Метрика | Тип | Как считаем | Сейчас (оценка) | Цель через 3 месяца после запуска |
|---|---------|-----|-------------|-----------------|-----------------------------------|
| 1 | **Время обнаружения зависшего или потерянного заказа (MTTD)** | Техническая | От момента, когда заказ вышел за норму, до первого сигнала команде | Дни–недели (узнаём по жалобе клиента) | ≤ 15 минут (по автоматическому алерту) |
| 2 | **Время поиска причины проблемы с заказом (MTTR-diagnosis)** | Техническая | От сигнала до понимания, на каком шаге и почему заказ встал | Часы–дни | ≤ 15 минут |
| 3 | **Доля заказов с полной цепочкой трейсов** (покрытие) | Техническая | Заказы, у которых в трейсе есть все ожидаемые шаги / все заказы | 0% | ≥ 99% новых заказов |
| 4 | **Число потерянных и зависших заказов в месяц** | Бизнес | Заказы, не двигавшиеся дольше порога по статусу (раздел 4.5), и заказы без следующего шага | Не измеряется | Снижение минимум в 5 раз за 3 месяца, цель — 0 потерянных |
| 5 | **Доля заказов, сделанных в обещанный срок (3 недели)** и число жалоб на сроки | Бизнес | Заказы, закрытые не позже срока / все заказы; жалобы в неделю | Низкая, растёт число жалоб | Рост доли в срок, жалобы на сроки сокращаются вдвое |
| 6 | **Доля вопросов «где мой заказ», закрытых поддержкой без разработчика** | Бизнес / операционная | Обращения, решённые первой линией / все обращения по заказам | Около 0% | ≥ 80% |

## 4. Предлагаемое решение

### 4.1. Ключевая идея: «один заказ — одна цепочка (trace)»

Обычный трейс живёт секунды (запрос ушёл, ответ пришёл). Заказ живёт недели. Поэтому делаем так:

1. **У каждого заказа один постоянный `trace_id`.** Если идентификатор заказа — UUID (128 бит), используем его без дефисов. Если нет — создаём `trace_id` при INITIATED и сохраняем в таблице заказов (в Shop DB и MES db).
2. **Каждый шаг заказа — отдельный спан** с этим же `trace_id`: `order.initiated`, `order.file_uploaded`, `order.submitted`, `price.calculate`, `order.price_calculated`, `crm.approve`, `manufacturing.started`, … `order.closed`. Внутри шага обычные автоматические спаны: HTTP-запрос, запрос в БД, публикация и получение сообщения, чтение из S3.
3. **Контекст передаётся дальше** стандартным способом W3C (`traceparent`): по HTTP — в заголовке, по RabbitMQ — в заголовках сообщения, в БД — в колонке `trace_id`. Когда заказ «просыпается» через дни (например, продавец нажал «Подтвердить»), сервис берёт `trace_id` из БД и продолжает ту же цепочку.
4. **Заказ можно найти по `order.id`** через поиск по атрибутам и увидеть всю историю: какие шаги прошли, сколько ждали, где сейчас.

Почему так: другие схемы («отдельный трейс на каждый шаг с ссылками») сложнее читать поддержке. Одна цепочка на заказ естественно отвечает на вопрос «что с заказом».

### 4.2. Технологии и почему они

| Задача | Выбор | Почему |
|--------|-------|--------|
| Стандарт и библиотеки | **OpenTelemetry** (OTel) | Открытый стандарт для Java и C#. Не привязывает нас к поставщику. Часть сбора идёт автоматически |
| Java (Shop API, CRM API) | **OTel Java agent** | Подключается параметром запуска без переписывания кода. Умеет HTTP, JDBC, Spring, RabbitMQ |
| C# (MES API) | **OTel .NET SDK** + ручные спаны на шагах заказа | Автоинструментация HTTP и PostgreSQL есть. Для RabbitMQ и расчёта цены добавляем немного ручного кода |
| Приём и обработка | **OpenTelemetry Collector** | Единая точка приёма. Здесь удаляем личные данные, делаем выборку (sampling), буферизуем, повторяем отправку при сбоях |
| Хранение трейсов | **Grafana Tempo** с хранением в S3-совместимом бакете | Дешёвое хранение (объектное хранилище, без тяжёлой индексной БД), простая эксплуатация для команды с одним DevOps, поиск по атрибутам (TraceQL) |
| Просмотр | **Grafana** (уже планируется в задании 2 для метрик) | Один интерфейс для метрик, логов и трейсов. Поиск заказа по номеру, таймлайн заказа |
| Логи | Из задания 2 (JSON-логи с `order.id` и `trace_id`) | Из трейса можно перейти в логи конкретного шага |

Альтернатива: Jaeger с OpenSearch или Elasticsearch. Работает, но хранилище тяжелее и дороже в сопровождении. Для нашей команды выбираем Tempo.

### 4.3. Новые компоненты и доработки (см. диаграмму варианта 1)

**Новые контейнеры (красные)**

| Компонент | Что делает |
|-----------|------------|
| **OpenTelemetry Collector** | Принимает спаны (OTLP) от Shop API, CRM API, MES API. Удаляет личные данные, применяет выборку, отправляет в Tempo |
| **Grafana Tempo** | Хранит трейсы, выполняет поиск по `order.id` и другим атрибутам |
| **Trace storage (S3-бакет)** | Отдельный бакет для блоков трейсов. Срок хранения 90 дней |
| **Grafana** | Интерфейс для поддержки и разработчиков: поиск заказа, таймлайн, дашборды |
| **Support / Developer (люди)** | Пользователи системы трейсинга |

**Доработки существующих контейнеров (красные метки «+ OTel» на диаграмме)**

| Контейнер | Что доработать |
|-----------|----------------|
| Shop API (Java) | Подключить OTel Java agent; создавать `trace_id` заказа; спаны шагов INITIATED, FILE_UPLOADED, SUBMITTED; писать `trace_id` в БД |
| CRM API (Java) | Java agent; читать `trace_id` из БД и сообщений; спаны публикации в очередь, получения, подтверждения продавцом, закрытия; пробрасывать контекст в заголовки RabbitMQ |
| MES API (C#) | .NET SDK; ручные спаны на расчёте цены, назначении оператору, смене статусов; чтение и запись контекста в заголовках RabbitMQ; приём запросов внешних клиентов в новом или связанном трейсе (раздел 6.3) |
| Messages Queue (RabbitMQ) | Без изменения брокера. Договариваемся о формате: `traceparent` и `order.id` в заголовках каждого сообщения; DLQ-сообщения сохраняют заголовки |
| Фронтенды (Vue, React) | Второй этап, опционально: OTel Web SDK, чтобы начало цепочки было видно из браузера |
| Shop DB, MES db | Колонка `trace_id` в таблицах заказов (миграция); без других изменений |

**Выборка (sampling) и срок хранения**
- Трейсы шагов заказов (есть `order.id`) сохраняем **на 100%**: их немного (сотни–тысячи заказов в месяц), и именно они нужны.
- Остальные запросы (например, частое обновление дашборда MES) — выборка 5–10%, но **всегда сохраняем ошибки и медленные запросы** (tail-based sampling в Collector).
- Срок хранения в Tempo — 90 дней. Заказы живут дольше, поэтому история статусов остаётся в таблице истории в БД как источник истины, а трейс — инструмент диагностики.

**Как заказ выглядит в трейсе (пример)**

```
order 7f3a... (b2c)
├─ order.initiated            shop-api      12:01:03
├─ order.file_uploaded        shop-api      12:03:40   файл 18 МБ, 1.2 млн полигонов
├─ order.submitted            shop-api      12:04:10
├─ crm.publish_to_queue       crm-api       12:04:12   → очередь mes.price.request
├─ queue.wait                 rabbitmq      12:04:12 → 12:21:44   (ждал 17 мин 32 с)
├─ price.calculate            mes-api       12:21:44 → 12:49:02   (27 мин, result=ok)
├─ order.price_calculated     mes-api       12:49:03
├─ crm.waiting_approval       crm-api       12:49:05 → (ещё не подтверждён, 3 дня 2 ч)
```

Сразу видно, где время: ожидание в очереди, тяжёлый расчёт, три дня ожидания продавца.

### 4.5. Дополнительное задание: автоматический мониторинг прохождения заказа и алертинг

Цель: не ждать, пока кто-то откроет Grafana, а получать сигнал сразу, когда заказ идёт не так.

**Что добавляется (зелёные элементы на диаграмме варианта 2):**

| Компонент | Что делает |
|-----------|------------|
| **Order Flow Monitor** (небольшой сервис, Spring Boot + своя маленькая PostgreSQL-схема) | Получает от Collector спаны статусов заказов, хранит «последнее известное состояние» каждого заказа (статус, время, источник). Раз в минуту сравнивает с нормами по статусам и считает метрики: сколько заказов зависло, возраст самого старого в каждом статусе |
| **Prometheus** (из задания 2) | Хранит метрики от Order Flow Monitor и метрики спанов от Tempo, содержит правила алертов |
| **Alertmanager** (из задания 2) | Группирует алерты, убирает дубли, направляет по важности |
| **Notification channels** | Чат команды (Telegram или Slack), e-mail поддержке и продакту, тикеты в Jira, срочное оповещение дежурному |
| Связи | Collector → Order Flow Monitor (спаны статусов); Tempo → Prometheus (метрики по спанам: частота, ошибки, длительность по сервисам и шагам); Order Flow Monitor → Prometheus (метрики заказов); Prometheus → Alertmanager → каналы; Prometheus → Grafana (дашборды) |

Prometheus, Alertmanager и Grafana запланированы ещё в задании 2 для метрик. Здесь они показаны как новые элементы, потому что на исходной C4-диаграмме их нет. Отдельный сервис из задания 2 (расчёт бизнес-метрик заказов по базам) можно объединить с Order Flow Monitor, чтобы не писать два похожих сервиса.

**Как работает «мониторинг по отсутствию»**

Проблема потерянных сообщений в том, что ошибки **нет**: сообщение просто не пришло. Поэтому недостаточно искать красные спаны. Order Flow Monitor знает ожидаемую цепочку шагов и допустимое время на каждый переход. Если после шага N за отведённое время не появился шаг N+1, это сигнал.

**Правила (стартовые, уточнить по реальным данным за 2–4 недели)**

| Ситуация | Норма | Предупреждение (чат + тикет) | Критично (дежурный + письмо поддержке и продакту) |
|----------|-------|------------------------------|---------------------------------------------------|
| После SUBMITTED нет публикации в очередь (T2) | ≤ 5 минут | > 15 минут | > 1 час |
| Сообщение в очереди без обработки (T3) | ≤ 10 минут | > 10 минут | > 30 минут |
| SUBMITTED → PRICE_CALCULATED (T4) | ≤ 30 минут | > 30 минут | > 2 часа |
| Расчёт цены завершился ошибкой или таймаутом | 0 | любой случай | серия ≥ 3 за час |
| Сообщение попало в DLQ или ≥ 3 повторов (T3) | 0 | любой случай | ≥ 5 за час |
| PRICE_CALCULATED → MANUFACTURING_APPROVED (T6, человек) | ≤ 1 рабочий день | > 1 рабочий день (напоминание продавцу) | > 3 рабочих дней (эскалация продакту) |
| MANUFACTURING_APPROVED → MANUFACTURING_STARTED (T7) | ≤ 1 рабочий день | > 1 рабочий день | > 3 рабочих дней |
| Расхождение статусов CRM и MES (T7) | нет | любое > 15 минут | ≥ 10 заказов |
| SHIPPED → CLOSED (T8) | по сроку доставки | позже срока на 2 дня | позже срока на 7 дней |
| Всплеск ошибок или рост времени шагов по сервису (метрики спанов) | в пределах нормы | > 1% ошибок за 5 минут | > 5% |

**Что происходит при срабатывании**
1. Order Flow Monitor / Prometheus формируют алерт с аннотацией: статус, источник заказа, возраст, число затронутых заказов, ссылка на «таймлайн заказа» в Grafana и список из 10 самых старых номеров заказов (номера не лежат в метках, чтобы не раздувать хранилище).
2. Alertmanager отправляет в канал по важности: предупреждение — чат и тикет в Jira (автоматически), критично — ещё и дежурному (звонок или пейджер) и письмо в поддержку и продакту, если затронуты клиенты.
3. Для заказов внешних API-клиентов поддержка получает отдельное сообщение с `client.id`, чтобы упреждающе связаться с клиентом.
4. Повторы одного алерта гасятся (группировка, интервал повтора), тикет не дублируется.
5. Для каждого алерта есть краткая инструкция (runbook): что значит, что проверить, кого звать.

**Дашборд «Здоровье заказов»** (для продакта и менеджеров): число заказов по статусам, самый старый заказ в статусе, топ зависших заказов со ссылками на трейс, время по шагам (ожидание в очереди, расчёт, подтверждение продавцом, производство), разрез B2C и API.

Диаграмма варианта 2: [C4-containers-tracing-alerting.png](./C4-containers-tracing-alerting.png), исходник [SVG](./C4-containers-tracing-alerting.svg). Зелёным выделены новые элементы и связи, красное из варианта 1 сохранено.

## 5. Компромиссы: когда трейсинг не поможет, невозможен или слишком дорог

| Случай | Что происходит | Как справляемся |
|--------|----------------|-----------------|
| **Сервис упал до публикации сообщения** | Спана «ошибка» нет, потому что нечему его создавать. Классическая ошибка не видна | Ловим **отсутствие** следующего шага (раздел 4.5). Надёжнее вместе с паттерном Outbox из задания 1 (инициатива И-2): тогда событие хотя бы записано в БД |
| **Старые заказы** | Заказы, созданные до внедрения, не имеют трейса | Ретроспективно восстановить нельзя. Для них используем историю статусов в БД. Новые заказы получают трейс с момента выката |
| **Внешние системы** (транспортная компания, внешние API-клиенты) | Мы не можем заставить их передавать наш контекст | Принимаем их `traceparent` как подсказку, но заказ идёт в своей цепочке. Интеграция с транспортной компанией на схеме отсутствует, поэтому T8 покрываем частично |
| **MES куплена вместе с исходным кодом** | Доработка возможна, но у вендора может быть своя ветка обновлений. Каждая наша правка усложнит слияние обновлений | Минимум правок в коде: SDK, обёртки вокруг публикации и получения сообщений, ручные спаны только на шагах заказа. Хранить правки отдельным слоем |
| **RabbitMQ в .NET** | Автоинструментация ограничена, не всё подхватывается само | Несколько строк кода для записи и чтения `traceparent` в заголовках. Один раз, в общей обёртке |
| **Расчёт цены как «чёрный ящик»** | Трейсинг покажет, что расчёт занял 27 минут, но не покажет, почему алгоритм медленный | Дополнительно профилировать код расчёта и добавлять вложенные спаны на тяжёлые этапы. Для этого нужна работа разработчика C# |
| **Один C#-разработчик** | Узкое место по людям при доработке MES | Подключить тимлида (бывший C#-разработчик), заложить это в план найма (инициатива И-10) |
| **Нагрузка и объём данных** | Трейсинг добавляет нагрузку (обычно единицы процентов CPU) и объём хранения | Выборка для обычных запросов, 100% только для шагов заказов, 90 дней хранения, мониторинг размера бакета |
| **Высокая кардинальность** | `order.id` в метках метрик «раздувает» Prometheus | `order.id` только в трейсах и логах, в метриках — статус и источник (как в задании 2) |
| **Эксплуатация** | Новые сервисы (Collector, Tempo, Order Flow Monitor) надо поддерживать, DevOps один | Простые режимы развёртывания (один экземпляр Tempo в монолитном режиме), всё описано как код, мониторинг самих компонентов. Дополнительный аргумент за второго DevOps |
| **Трейсинг ≠ источник истины по статусам** | Трейс может потеряться при сбое сбора | История статусов остаётся в БД. Трейсинг — диагностика и сигналы |
| **Фронтенд-трассировка** | Добавляет вес скрипта и риск утечки данных | Откладываем на второй этап, включаем после оценки пользы |
| **Когда не стоит усложнять** | Если заказов станет мало и все шаги в одном приложении | Тогда хватило бы логов и метрик. В нашем случае (три приложения, очередь, рост заказов) трейсинг оправдан |

## 6. Безопасность

### 6.1. Доступ внутри компании

- **Вход только по корпоративной учётной записи (SSO / OIDC) с двухфакторной аутентификацией.** Отдельных локальных паролей Grafana нет, кроме аварийной учётной записи администратора, пароль в хранилище секретов.
- **Роли в Grafana:**
  - **Поддержка и продажи** — только просмотр: поиск заказа по номеру, таймлайн заказа, дашборд «Здоровье заказов». Без прямого доступа к сырым трейсам других сервисов.
  - **Разработчики** — просмотр трейсов и логов (Explore), без права менять настройки.
  - **DevOps / администраторы** — управление Grafana, Tempo, Collector, правилами алертов.
- Права выдаются по принципу минимально необходимых. При увольнении или смене роли доступ отзывается (учётная запись в корпоративном каталоге).
- **Журнал аудита:** фиксируем, кто и когда смотрел заказы клиентов (поиск по `order.id`).
- Доступ к Grafana только из корпоративной сети или через VPN. Публичного адреса у Grafana, Tempo и Collector нет.

### 6.2. Защита данных в самих трейсах

- **Collector удаляет или хэширует** любые поля, похожие на личные данные (e-mail, телефон, адрес, имя), токены и заголовки авторизации. Работает список разрешённых атрибутов (allow-list): всё, чего в списке нет, отбрасывается.
- В `db.statement` значения параметров не записываем.
- Тела запросов и ответов, 3D-файлы и платёжные данные в трейсы не попадают (раздел 2.2).
- Пользователи в трейсах обозначены обезличенным идентификатором или ролью.
- Срок хранения 90 дней, затем данные удаляются автоматически (политика бакета).

### 6.3. Внешний контур и граница доверия

- **Снаружи доступа к трейсингу нет.** Внешние клиенты API и покупатели магазина не видят Collector, Tempo и Grafana.
- Если внешнему клиенту нужен статус заказа, он получает его через публичный API статуса (инициатива И-6 из задания 1) только по своим заказам и без деталей трейсов.
- **Входящий `traceparent` от внешнего клиента не доверяем.** Не используем его как `trace_id` заказа, чтобы клиент не мог подменить или «засорить» чужую цепочку. Входящий внешний контекст сохраняем как ссылку (link), а цепочка заказа ведётся по нашему `trace_id`. Заголовки `tracestate` и `baggage` извне отбрасываем на границе (MES API, будущий API Gateway).

### 6.4. Защита каналов и инфраструктуры

- **Шифрование передачи (TLS):** сервисы → Collector, Collector → Tempo, Grafana → Tempo, Tempo → S3. Между сервисами и Collector используем взаимную аутентификацию (mTLS) или токены, выданные каждому сервису.
- **Сетевые правила:** порты Collector (OTLP) открыты только для серверов приложений; Tempo доступен только Collector и Grafana; бакет трейсов доступен только по ролям IAM сервиса Tempo, публичного доступа нет, включено шифрование хранилища.
- **Защита от перегрузки и злоупотреблений:** лимиты памяти и размера пачек в Collector, ограничение размера трейса и числа атрибутов, лимиты запросов к Tempo, чтобы сбой или «шумный» сервис не уронил систему сбора.
- **Секреты** (токены, ключи) хранятся в хранилище секретов, не в репозитории и не в конфигурации в открытом виде.
- **Разделение окружений:** dev, release и prod пишут в раздельные экземпляры (или раздельные арендаторы) Tempo, чтобы тестовые данные не смешивались с боевыми, а доступы различались.
- **Конфигурации** Collector, Tempo и правил алертов хранятся как код (с ревью изменений).
- **Alertmanager и каналы оповещений:** в уведомления не попадают личные данные клиентов, только номера заказов, статусы и ссылки на Grafana (за авторизацией).
