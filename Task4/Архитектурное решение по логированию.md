# Архитектурное решение по логированию

Технический документ. Проект: «Александрит» (онлайн-магазин, CRM, MES, внешний API).

Что такое логирование, простыми словами: это «бортовой журнал» каждого сервиса. Сервис записывает, что с ним происходит: получил заказ, посчитал цену, не смог связаться с очередью. Когда клиент пишет «у меня что-то сломалось», разработчик или поддержка открывают журнал и видят, что произошло на самом деле, а не со слов клиента.

Диаграмма к документу (новое — красным, источники логов отмечены метками с очерёдностью внедрения): [C4-containers-logging.png](./C4-containers-logging.png)

Связь с предыдущими заданиями: метрики (задание 2) отвечают «что-то не так», трейсинг (задание 3) отвечает «где заказ», логи отвечают «что именно произошло и почему». Три инструмента связаны общими полями `order_id` и `trace_id`.

## 1. Анализ системы: какие логи собираем и откуда

### 1.1. Источники логов (отмечены на диаграмме)

| Система | Что даёт в логах | Приоритет | Как собираем |
|---------|------------------|-----------|--------------|
| **MES API** (C#) | Приём заказов от внешних клиентов, расчёт цены, назначение операторам, смена статусов; ошибки и таймауты | **Волна 1** | Serilog в JSON, файл или stdout → Fluent Bit |
| **CRM API** (Java) | Передача заказа в очередь, получение сообщений, подтверждение продавцом, закрытие заказа; ошибки обработки сообщений | **Волна 1** | Logback в JSON → Fluent Bit |
| **RabbitMQ** | Подключения и отключения потребителей, тревоги по памяти и диску, служебные события; сообщения, попавшие в DLQ (пишет потребитель) | **Волна 1** | Журнал брокера (формат JSON) → Fluent Bit на его сервере |
| **Shop API** (Java) | Создание заказа, загрузка 3D-файла, оформление; ошибки записи в БД и S3 | Волна 2 | Logback в JSON → Fluent Bit |
| **Shop DB, MES db** (PostgreSQL, управляемые) | Медленные запросы, блокировки, ошибки подключения | Волна 2 | Выгрузка журналов через API облака (Fluent Bit или небольшая задача по расписанию) |
| **Internet Shop, CRM, MES (фронтенды)** | Только ошибки в браузере (JavaScript) | Волна 3 | Браузер отправляет ошибки на endpoint своего API, дальше как обычные логи этого API. Отдельных прямых связей на схеме нет |
| **3D files storage (S3)** | Журнал доступа к бакету (кто и когда читал и писал файлы) | Волна 3 (по желанию) | Серверное журналирование доступа в отдельный бакет → Fluent Bit |
| **Серверы EC2** (ОС) | Входы по SSH, действия администраторов (журналы безопасности) | Волна 3 | Fluent Bit (syslog/auth) |

На схеме метка `L` — только логи, `L+T` — логи и трейсинг одновременно (раздел 4).

### 1.2. Формат логов: структурированный JSON

Каждая запись — одна строка JSON. Не «Order 123 failed for user 5», а набор полей, по которым можно искать. Обязательные поля в каждой записи:

| Поле | Зачем |
|------|-------|
| `@timestamp` (UTC, ISO 8601) | Когда |
| `level` | Уровень (INFO, WARN, ERROR…) |
| `service`, `version`, `env`, `host` | Какой сервис и версия, какое окружение (dev / release / prod), какой сервер |
| `event` | Короткое неизменное имя события (например `order.status_changed`). По нему строятся поиск, дашборды и алерты |
| `message` | Человекочитаемое сообщение |
| `order_id` | Номер заказа (если запись относится к заказу) |
| `trace_id`, `span_id` | Связь с трейсингом (задание 3) |
| `request_id` | Идентификатор входящего запроса (для связи записей одного запроса) |

Пример записи:

```json
{
  "@timestamp": "2026-10-13T12:49:02.512Z",
  "level": "INFO",
  "service": "mes-api",
  "version": "1.14.2",
  "env": "prod",
  "host": "mes-api-1",
  "event": "price.calculation_finished",
  "message": "Price calculation finished",
  "order_id": "7f3a1c52-0d4b-4f8e-9a77-5b1c2d3e4f50",
  "customer_id": "c-10432",
  "source": "api",
  "client_id": "partner-17",
  "trace_id": "7f3a1c520d4b4f8e9a775b1c2d3e4f50",
  "request_id": "b9c1e2f0-77aa-4c1a-8d21-0e5f6a7b8c9d",
  "duration_ms": 1643000,
  "result": "ok",
  "model_polygons": 1200000
}
```

## 2. Список логов уровня INFO

INFO — «нормальная жизнь системы»: важные бизнес-события и их результат. Общие поля (раздел 1.2) есть в каждой записи, ниже перечислены только поля, специфичные для события.

| № | Система | Событие (`event`) | Когда пишем | Дополнительные поля |
|---|---------|-------------------|-------------|---------------------|
| 1 | Shop API | `order.created` | Пользователь завёл заказ или положил товар в пустую корзину (INITIATED) | `order_id`, `customer_id`, `source=b2c` |
| 2 | Shop API | `file.uploaded` | Загружен 3D-файл или создан в конструкторе (FILE_UPLOADED) | `order_id`, `customer_id`, `file_id`, `size_bytes`, `format`, `duration_ms` |
| 3 | Shop API | `order.submitted` | Нажата кнопка «Сделать заказ» (SUBMITTED) | `order_id`, `customer_id`, `items_count` (без цен и состава) |
| 4 | Все три API | **`order.status_changed`** | Любое изменение статуса заказа | `order_id`, `customer_id`, `status_from`, `status_to`, `changed_by` (система / роль человека) |
| 5 | CRM API | `order.picked_up` | Заказ из Shop DB подхвачен для передачи в производство (по допущению из задания 3) | `order_id`, `source` |
| 6 | CRM API, MES API | `message.published` | Отправлено сообщение в RabbitMQ | `message_id`, `exchange`, `routing_key`, `message_type`, `order_id` |
| 7 | CRM API, MES API | `message.received` | Получено сообщение из RabbitMQ | `message_id`, `queue`, `message_type`, `order_id`, `redelivered`, `queue_wait_ms`, `processing_ms` |
| 8 | CRM API | `order.approved` | Продавец подтвердил заказ (MANUFACTURING_APPROVED) | `order_id`, `seller_id`, `wait_ms` (сколько ждал подтверждения) |
| 9 | CRM API | `order.closed` | Заказ закрыт (CLOSED) | `order_id`, `reason` (сообщение транспортной компании / вручную), `closed_by` |
| 10 | MES API | `api.order_received` | Внешний клиент создал заказ через API | `order_id`, `client_id`, `request_id`, `file_id`, `response_ms` (без содержимого запроса) |
| 11 | MES API | `price.calculation_started` | Начат расчёт цены | `order_id`, `file_id`, `model_polygons`, `queue_wait_ms` |
| 12 | MES API | `price.calculation_finished` | Расчёт закончен (PRICE_CALCULATED) | `order_id`, `duration_ms`, `result` (ok / error / timeout) |
| 13 | MES API | `order.assigned` | Заказ назначен оператору | `order_id`, `operator_id`, `assign_ms` |
| 14 | RabbitMQ | `broker.consumer_connected` / `broker.consumer_disconnected` | Подключение и отключение потребителя | `queue`, `consumer`, `client_service` |
| 15 | Все сервисы | `app.started` / `app.stopped` | Запуск и остановка сервиса | `version`, хэш конфигурации |
| 16 | Все сервисы | `auth.login_succeeded` / `auth.login_failed` | Вход пользователя (аутентификация) | `user_id` (внутренний), `role`, `ip` (только в индексе безопасности, раздел 7.1) |
| 17 | Все сервисы | `audit.admin_action` | Действия администратора: смена ролей, прав, настроек | `actor`, `action`, `target` |
| 18 | Все API | `http.request` (access-лог) | Каждый HTTP-запрос (в отдельном индексе) | `method`, `route` (шаблон без ID), `status`, `duration_ms`, `client_id`, `request_id` |

**Что намеренно не пишем на уровне INFO** (чтобы не утонуть в шуме и не раздувать хранилище):
- Каждое обновление дашборда MES и проверки здоровья (`/health`), записи об успешных обычных чтениях списков.
- Внутренние шаги, которые не помогают разобрать заказ (промежуточные значения алгоритма).
- Содержимое запросов и ответов целиком.

## 3. Другие уровни логирования

| Уровень | Когда используем | Пример | Что происходит дальше |
|---------|------------------|--------|-----------------------|
| **ERROR** | Операция не выполнена, нужен разбор. Всегда со стеком (в обрезанном виде), `order_id` и причиной | Не удалось записать заказ в БД; расчёт цены завершился ошибкой; исключение при обработке сообщения | Попадает в алерты (раздел 9.1). Хранится дольше, чем INFO |
| **WARN** | Система справилась, но что-то неправильно или «на грани» | Повторная попытка отправки сообщения; сообщение ушло в DLQ; запрос дольше порога (> 1 с); два оператора взяли один заказ (конфликт); превышен лимит клиента API; расчёт дольше 20 минут | Источник предупреждений и правил раннего обнаружения |
| **FATAL (CRITICAL)** | Сервис не может продолжать работу | Нет подключения к БД на старте; потерян доступ к очереди | Сразу срочный алерт дежурному |
| **DEBUG** | Подробности для разработчика. **В prod выключен по умолчанию** | Параметры расчёта цены, развёрнутые ответы смежных сервисов | В prod включается временно (до часа) для конкретного сервиса или заказа, с автоматическим возвратом. Хранится 3 дня. Только в dev и release включён постоянно |
| **TRACE** | Самая подробная отладка | Каждый шаг алгоритма | Не используем в prod никогда |

Правила:
- **Один уровень на смысл.** Ожидаемые «нет данных» (пустая корзина) — не ERROR.
- **Динамическое повышение детализации.** Уровень меняется без перезапуска (по настройке сервиса или переключателю), чтобы расследовать «плавающие» проблемы без релиза.
- **Не логировать и не пробрасывать наружу** пароли, токены, персональные данные (раздел 7).

## 4. Мотивация

### 4.1. Почему нужно логирование

- **Сейчас разбор идёт «со слов клиента».** Клиент говорит «что-то не так», разработчик не может воспроизвести проблему и не видит, что происходило в сервисе в тот момент.
- **Часть логов, скорее всего, разбросана по серверам.** Три приложения, два вида баз и очередь живут на разных машинах. Чтобы собрать картину по одному заказу, нужно идти на каждый сервер вручную. Единого места с поиском по номеру заказа нет.
- **Логи исчезают.** Файлы на одном сервере ротируются и удаляются; заказ живёт неделями, жалоба приходит позже.
- **Метрики и трейсинг не заменяют логи.** Метрика скажет «ошибок стало больше», трейс покажет «встал на расчёте», но причину («файл повреждён, сторонний формат») обычно только в тексте ошибки.
- **Мы уже теряем клиентов.** Внешним клиентам API нужен быстрый и понятный ответ, что произошло с их заказом.

### 4.2. Что получает компания

| Кто | Что получает |
|-----|--------------|
| **Поддержка** | Ищет заказ по номеру и сама видит, что произошло, без обращения к разработчикам |
| **Разработчики** | Находят причину сбоя по реальным данным: ошибка, стек, входные параметры. Меньше «не воспроизводится» |
| **Продакт и менеджеры** | Объективная картина для ответа клиентам (особенно B2B): что случилось, когда и по чьей стороне |
| **Безопасность** | Видно, кто и когда входил, какие необычные запросы были, не скачивает ли кто-то массово данные |
| **Бизнес** | Меньше времени уходит на разбор инцидентов, ниже риск потери клиентов из-за «непонятных» ошибок |

### 4.3. Метрики, на которые повлияет внедрение

Текущие значения замерить в первые 2–4 недели (по обращениям и трекеру), цели — ориентиры на 3 месяца после запуска.

| № | Метрика | Тип | Сейчас (оценка) | Цель |
|---|---------|-----|-----------------|------|
| 1 | **Время от обращения до установленной причины** по проблемному заказу | Техническая | Часы–дни | ≤ 30 минут |
| 2 | **Доля обращений типа «где заказ» и «почему ошибка», закрытых поддержкой без разработчиков** | Бизнес / операционная | Около 0% | ≥ 70% |
| 3 | **Доля ошибок, найденных системой раньше, чем клиентом** (алерт появился до жалобы) | Техническая | Низкая (узнаём от клиентов) | ≥ 80% |
| 4 | **Доля инцидентов с неустановленной причиной («не воспроизводится»)** | Техническая | Высокая | ≤ 10% |
| 5 | **Трудозатраты разработчиков на разбор инцидентов** (человеко-часы в месяц) | Бизнес (стоимость) | Не измеряется, много | Снижение минимум на 50% |

## 5. Очерёдность: для каких систем логирование и трейсинг настраиваем в первую очередь

Команда не может сделать всё сразу (один DevOps, один C#-разработчик). Поэтому три волны. Они определены по принципу: **сначала там, где заказы теряются и где это дороже всего**.

| Волна | Системы | Срок (ориентир) | Почему |
|-------|---------|-----------------|--------|
| **1** | **MES API, CRM API, RabbitMQ**: логи + трейсинг | Недели 1–6 | Здесь (по заданию 3, точки T2–T7) заказы теряются и зависают. Самые дорогие жалобы: внешние клиенты API и потерянные контракты. Чтобы восстановить путь заказа, нужны **оба конца очереди**: если снять данные только с одного, цепочка рвётся и пользы почти нет. Поэтому делаем их вместе, целиком «путь заказа API-клиента» |
| **2** | **Shop API** (+ файлы в S3), логи **Shop DB и MES db** (медленные запросы) | Недели 6–10 | Shop API: ошибки сразу видны клиенту (и частично через Яндекс Метрику), путь короче и проще. Логи БД нужны для разбора тормозов дашборда MES, это дёшевая настройка на стороне облака |
| **3** | **Фронтенды** (только ошибки браузера), журналы доступа S3, журналы безопасности серверов | Недели 10+ | Меньше всего влияют на потерянные заказы; у фронтендов выше риск попадания персональных данных, поэтому делаем после настройки маскирования |

Почему именно так:
1. **Эффект на деньги и клиентов.** Волна 1 покрывает самый дорогой путь (внешние API-клиенты, расчёт цены, передача между CRM и MES).
2. **Зависимости.** Трейсинг передаёт контекст через заголовки сообщений. Пока не настроены обе стороны очереди, связи нет.
3. **Узкое место по людям.** Волна 1 нагружает единственного C#-разработчика. Подключаем тимлида (он раньше писал на C#), Java-разработчики делают CRM API и общий шаблон логирования, DevOps разворачивает платформу.
4. **Что откладываем осознанно.** Frontend-логи и логи безопасности ОС ценны, но не уменьшают текущие потери заказов.

Это уточняет порядок из задания 3: подготовка на dev (Shop API и CRM API) может идти параллельно, а на prod включаем по волнам.

## 6. Предлагаемое решение

### 6.1. Общая схема (см. диаграмму)

```
Сервис (Serilog / Logback, JSON)  →  Fluent Bit (на сервере)  →  OpenSearch  →  Dashboards / Alerting
 + логи управляемых БД (через API облака)                          ↓
                                                       снимки (snapshots) в S3 для архива
```

### 6.2. Выбор технологий

| Задача | Выбор | Почему |
|--------|-------|--------|
| Формат | JSON, поля из раздела 1.2 | Поиск по полям, а не по тексту |
| Библиотеки в приложениях | Java: Logback + JSON-кодировщик (logstash-logback-encoder), MDC для `order_id`, `trace_id`; C#: Serilog (JSON, enrichers) | Стандарт для платформ, минимум своего кода |
| Сбор и доставка | **Fluent Bit** | Лёгкий, бесплатный (Apache 2.0), умеет буферизовать на диск и повторять отправку, маскировать данные, читать файлы, stdout и syslog |
| Хранение и поиск | **OpenSearch** (управляемый сервис) | Подробно в разделе 10. Бесплатная лицензия, встроенные безопасность, алерты и поиск аномалий |
| Интерфейс | **OpenSearch Dashboards** | Поиск, дашборды, управление алертами. Для сквозного просмотра с метриками и трейсами можно подключить OpenSearch как источник данных в Grafana (из заданий 2–3) |
| Архив | **Снимки (snapshots) в S3-бакет** | Дешёвое долгое хранение |
| Каналы оповещений | Telegram/Slack, e-mail, Jira, дежурный (как в заданиях 2–3) | Единая схема уведомлений |

Размещение: управляемый кластер OpenSearch либо в Yandex Cloud (где уже живут БД), либо в AWS (рядом с EC2). Выбор по цене сетевого трафика между облаками и требованиям к хранению данных. Самостоятельная установка при одном DevOps не рекомендуется.

### 6.3. Новые компоненты и доработки

**Новые контейнеры (красные)**

| Компонент | Что делает |
|-----------|------------|
| **Log collectors (Fluent Bit)** | Агенты на серверах Shop API, CRM API, MES API и RabbitMQ плюс выгрузка логов управляемых БД. Маскируют чувствительные данные, буферизуют на диск при недоступности хранилища, отправляют в OpenSearch |
| **OpenSearch** | Хранит логи, индексы по системам и средам, поиск, встроенные алерты и поиск аномалий, автоматическое управление сроками хранения (ISM) |
| **OpenSearch Dashboards** | Интерфейс поиска и дашбордов для поддержки и разработчиков |
| **Log archive (S3)** | Снимки индексов для долгого хранения (аудит и события заказов) |
| **Notification channels** | Чат, e-mail, Jira, дежурный |
| **Support / Developer** | Пользователи системы |

**Доработки существующих систем**

| Система | Что доработать |
|---------|----------------|
| Shop API, CRM API (Java) | Logback в JSON; MDC с `order_id`, `request_id`, `trace_id`; общая библиотека-обёртка с маскированием; запрет логировать целые объекты (`toString` DTO); события из раздела 2 |
| MES API (C#) | Serilog в JSON; middleware, который добавляет `request_id` и `trace_id`; события из раздела 2; маскирование в destructuring-политиках |
| RabbitMQ | Включить журнал событий подключений в формате JSON, вывод в файл или stdout; потребители логируют `message.received` с `message_id` и признаком `redelivered`, DLQ-случаи как WARN |
| Управляемые БД | Включить журналирование запросов дольше 1 секунды, блокировок и ошибок подключения (настройки PostgreSQL в облаке), выгрузку журналов через API |
| Фронтенды (волна 3) | Endpoint приёма ошибок браузера в каждом API, фильтрация данных на стороне клиента |
| CI/CD | Шаблон логирования, чек-лист в pull request, автотест на отсутствие персональных данных в тестовых логах |

### 6.4. Как этим пользуется поддержка

Пример: клиент API пишет «заказ 7f3a… не пришёл». Сотрудник поддержки открывает Dashboards, вводит номер заказа и получает в хронологическом порядке все записи по этому заказу из всех сервисов: создан в MES API, сообщение отправлено, получено CRM API или нет, расчёт цены, ошибка. Если ошибка техническая, он отправляет ссылку разработчику. Из записи по `trace_id` можно перейти к трейсу заказа (задание 3).

## 7. Политика безопасности логов

### 7.1. Классификация данных в логах

| Категория | Примеры | Правило |
|-----------|---------|---------|
| **Запрещено всегда** | Пароли, токены, API-ключи, заголовки `Authorization` и cookie, полные номера банковских карт, CVV, содержимое 3D-файлов, секреты конфигурации | Никогда не попадают в логи. Если обнаружены — это инцидент безопасности (раздел 7.2, рубеж 3) |
| **Персональные данные** | ФИО, e-mail, телефон, адрес, дата рождения | В явном виде не пишем. Вместо этого внутренний идентификатор (`customer_id`, `seller_id`, `operator_id`). Если нужен признак (например, домен почты), то в маскированном виде |
| **Разрешено** | `order_id`, `customer_id`, `client_id`, `file_id`, статусы, длительности, размеры, коды ответов, имена сервисов | Основные поля для разбора |
| **Чувствительные технические** | IP-адреса пользователей | Пишем только в индекс безопасности с ограниченным доступом (раздел 7.3) |

### 7.2. Три рубежа защиты

1. **В коде.** Библиотека-обёртка и шаблоны логирования; маскирующие конвертеры Logback и Serilog; запрет логировать объекты целиком; проверка в ревью и автотест на отсутствие ПДн в тестовых логах.
2. **На агенте (Fluent Bit).** Фильтры по шаблонам: e-mail, телефоны, номера карт (с проверкой по алгоритму Луна), Bearer- и JWT-токены, пароли в параметрах адреса. Найденное маскируется или удаляется.
3. **В OpenSearch.** Конвейер приёма (ingest pipeline) как последний барьер. Дополнительно регулярная проверка индексов на паттерны чувствительных данных; найденное — алерт и разбор как инцидент (раздел 9.1).

### 7.3. Доступ к логам

| Роль | Доступ |
|------|--------|
| **Поддержка (L1)** | Только чтение: индекс событий заказов (`orders-events-*`) и готовые дашборды. Без доступа к access-логам, DEBUG, логам БД, инфраструктуре и индексу безопасности. Стеки и технические детали скрыты через ограничение на уровне полей |
| **Разработчики** | Чтение логов приложений: dev и release полностью; prod только приложение (INFO, WARN, ERROR) без индекса безопасности. Доступ к prod-логам — по необходимости, с журналированием запросов |
| **DevOps** | Все индексы, управление кластером, политиками хранения и снимками |
| **Безопасность / тимлид (аудитор)** | Индексы безопасности и аудита, журнал доступа к самим логам |
| **Сервисы и агенты** | Только запись в свои индексы (без права чтения) |
| **Внешние клиенты, покупатели** | Доступа нет. Информацию о статусе заказа клиенты API получают через публичный API статуса (инициатива И-6) |

### 7.4. Технические меры

- Вход только через корпоративную учётную запись (SSO) с двухфакторной аутентификацией, доступ из VPN или корпоративной сети; публичного адреса у OpenSearch и Dashboards нет.
- Шифрование данных при передаче (TLS) между агентами, кластером и пользователями, шифрование хранилища (at rest) и снимков.
- Роли и права настраиваются через модуль безопасности OpenSearch (RBAC, ограничения на уровне индексов и полей).
- **Журнал аудита доступа к логам** (кто и что искал) хранится 12 месяцев.
- Ключи агентов выдаются по одному на сервис, хранятся в хранилище секретов, ротируются.
- Разделение окружений: dev и release отдельно от prod (отдельные индексы и права).
- Права отзываются при смене роли или увольнении.
- **Удаление по запросу и сроки.** Прямых персональных данных в логах нет (только внутренние идентификаторы), поэтому удаление человека сводится к удалению связки идентификатора с личностью в БД. Дополнительно сроки хранения ограничены (раздел 8). Требования законодательства о персональных данных согласовать с юристом.

## 8. Политика хранения

### 8.1. Индексы

Отдельные индексы **по типу логов, среде и системе**, с ежедневной ротацией (или по размеру 30–50 ГБ, что наступит раньше):

| Тип | Имя индекса (шаблон) | Содержимое |
|-----|----------------------|------------|
| События заказов | `orders-events-prod` | Только ключевые события жизни заказа (`order.*`, `price.*`, `message.*`) со всех сервисов |
| Логи приложений | `app-<env>-<service>-YYYY.MM.dd` | INFO, WARN, ERROR каждого сервиса |
| Access-логи | `access-<env>-<service>-YYYY.MM.dd` | HTTP-запросы |
| Брокер и инфраструктура | `infra-<env>-<component>-YYYY.MM.dd` | RabbitMQ, ОС, БД |
| Безопасность и аудит | `security-<env>-YYYY.MM` | Вход, действия администраторов, доступ к логам |
| Отладка | `debug-<env>-<service>-YYYY.MM.dd` | DEBUG (только когда включён) |

Зачем отдельные индексы: разные сроки хранения и доступы (поддержке не нужен access-лог, безопасности нужен аудит), проще удалять и считать размер, проблема в одном сервисе не раздувает остальные.

### 8.2. Сроки хранения

| Тип | Горячее хранение (быстрый диск) | Общий срок | Потом |
|-----|-------------------------------|------------|-------|
| События заказов `orders-events-prod` | 30 дней | **12 месяцев** | Снимок в S3, затем удаление |
| Логи приложений prod | 14 дней | **90 дней** | Удаление (ERROR/WARN можно в снимок до 12 месяцев по решению безопасности) |
| Access-логи prod | 7 дней | **30 дней** | Удаление |
| Брокер и инфраструктура | 14 дней | 60 дней | Удаление |
| Безопасность и аудит | 30 дней | **12 месяцев** | Снимок в S3 |
| DEBUG | — | **3 дня** | Удаление |
| dev и release (все типы) | — | 7 дней | Удаление |

Почему события заказов хранятся 12 месяцев: заказ живёт неделями и месяцами, а жалоба или спор с клиентом API может прийти позже. Это очень небольшой объём (раздел 8.3) и самая ценная часть логов. Источник истины по статусам остаётся в БД, а логи нужны для диагностики и споров.

Сроки реализуются автоматически политиками управления жизненным циклом индексов (ISM): горячий → тёплый (без реплики, объединённые сегменты) → снимок и удаление.

### 8.3. Размер (оценка)

Исходных данных о фактическом объёме нет, поэтому расчёт — на сценарии допущений (**пересчитать по данным первых 2–4 недель**):

| Допущение | Значение |
|-----------|----------|
| HTTP-запросов в сутки суммарно по трём API (включая обновление дашборда MES) | 300 000 |
| Заказов в месяц | 5 000 (около 170 в сутки) |
| Записей INFO на заказ по всем сервисам | около 60 |
| Средний размер записи | 0,4 КБ (access) и 0,8 КБ (приложения) |

| Статья | Объём в сутки |
|--------|---------------|
| Access-логи: 300 000 × 0,4 КБ | около 120 МБ |
| События заказов: 170 × 60 × 0,8 КБ | около 8 МБ |
| Прочие INFO (сообщения, фон, служебные) | около 50 МБ |
| WARN и ERROR | около 10 МБ |
| RabbitMQ, БД, инфраструктура | около 20 МБ |
| **Итого в prod** | **около 0,2 ГБ в сутки** |

Размер на диске ≈ 1,2 × исходный объём (индексация и сжатие), для горячих индексов умножаем на 2 из-за реплики:
- Горячая часть 14 суток: 0,2 ГБ × 14 × 1,2 × 2 ≈ **7 ГБ**.
- Тёплая часть остальные 76 суток (без реплики): 0,2 × 76 × 1,2 ≈ **18 ГБ**.
- **Итого prod около 25 ГБ**. События заказов за год — порядка 3 ГБ. dev и release — единицы гигабайт.

С запасом на рост (заказов становится на 100 больше каждый месяц, плюс всплески и включение DEBUG) закладываем **кластер на 100–200 ГБ**. Если объём вырастет в 10 раз (до около 2 ГБ в сутки), потребуется порядка 250 ГБ для prod, что остаётся недорогим. Для таких объёмов достаточно небольшого кластера (3 узла с общим запасом по дискам). Размер шардов: один первичный шард на индекс (индексы маленькие).

Контроль объёма: метрика «объём логов в сутки по сервисам» (из самого OpenSearch) с алертом на резкий рост (раздел 9.2), ежемесячный разбор «самых шумных» источников.

## 9. От сбора логов к анализу логов

### 9.1. Алертинг (нужен)

Алерты настраиваем встроенным модулем алертинга OpenSearch. Уведомления идут в те же каналы, что в заданиях 2–3. Правила стартовые, уточняются по реальным данным.

| Что ловим | Условие | Предупреждение (чат + тикет) | Критично (дежурный, письмо поддержке/продакту) |
|-----------|---------|------------------------------|-----------------------------------------------|
| Всплеск ошибок сервиса | Число записей ERROR за 5 минут | > 20 или в 3 раза выше обычного | > 100 или в 10 раз выше обычного |
| FATAL | Любая запись | — | Сразу |
| Расчёт цены не удался | `price.calculation_finished` с `result` = error или timeout | Любой случай | ≥ 3 за час |
| Проблемы с сообщениями | Запись о попадании в DLQ; одно сообщение с `redelivered` ≥ 3 раз | Любой случай | ≥ 5 DLQ за час |
| Недопустимый переход статуса | `order.status_changed` вне разрешённой схемы (например CLOSED → SUBMITTED) | Любой случай | Серия |
| Конфликты операторов | WARN о назначении занятого заказа | > 10 за 10 минут | > 50 за 10 минут |
| Ошибки БД | «too many connections», медленные запросы > 3 с | Единичные | Серия или любая ошибка подключения |
| **Сервис «замолчал»** | Нет ни одной записи от сервиса 5 минут, хотя он должен работать (ловит падение сервиса и сбой сбора логов) | — | Сразу |
| Безопасность | Неудачных входов > 10 в минуту с одного IP или для одной учётной записи; много запросов к разным заказам от одного аккаунта | Подозрение | Подтверждено серией |
| Утечка чувствительных данных | В индексах найден шаблон e-mail, номера карты, токена | — | Любая запись: инцидент, разбор |
| Объём логов | Суточный рост > 5 раз по сервису | Да | > 10 раз (возможен цикл ошибок или атака) |

В каждом алерте: что произошло, какой сервис, пример `order_id`, ссылка на сохранённый поиск в Dashboards и (если есть) на трейс. Для каждого алерта есть краткая инструкция (runbook).

### 9.2. Поиск аномалий (нужен, в два этапа)

Аномалия — это отклонение от обычного поведения, даже если порог не пробит. Пример из задания: «было 4 создания заказа в минуту, стало 10 000».

**Что отслеживаем:**
- Число создаваемых заказов в минуту (по источникам b2c и api, а также по каждому `client_id`).
- Запросы в минуту по маршрутам и по клиентам API (подозрение на DDoS, скрейпинг, зациклившийся скрипт клиента).
- Доля ошибок и время ответа по сервисам.
- Неудачные входы, обращения к чужим заказам, обращения без `client_id`.
- Объём логов по сервисам.
- Обратная аномалия: **заказов нет совсем** в рабочее время (система «молчит» или сломана).

**Этап 1 (сразу): правила с базовой линией.** Сравнение текущего значения со значением за такое же время на прошлой неделе или за предыдущий час и порог кратности (например, в 5 раз больше обычного 10 минут подряд). Просто, понятно, мало ложных срабатываний, достаточно для примера из задания (рост с 4 до 10 000).

**Этап 2 (после 4–6 недель накопленных данных): встроенный в OpenSearch поиск аномалий** (метод Random Cut Forest). Детекторы на число запросов и заказов по клиентам и маршрутам; учитывает сезонность (будни и выходные, рост +100 заказов в месяц).

**Что происходит при срабатывании:**
1. Сообщение в канал и дежурному, с описанием: что выросло, у какого клиента, в какое время.
2. Проверка: это успех (рекламная акция, новый крупный клиент API), сбой клиента (зациклившийся скрипт) или атака.
3. Меры: временное ограничение по клиенту или IP (на API Gateway, когда появится по инициативе И-6; до этого вручную на уровне сети), блокировка источника, связь с владельцем клиента API.
4. Разбор причины и корректировка правил.

### 9.3. Дашборды и регулярный анализ

- **«Здоровье системы»**: ошибки и предупреждения по сервисам, объём логов, «молчащие» сервисы.
- **«Заказы»**: событий по статусам, ошибки расчёта, DLQ, конфликты операторов.
- **«API-клиенты»**: запросы, ошибки и задержки по `client_id`, выявление «шумных» клиентов.
- **«Безопасность»**: входы, подозрительная активность, доступы к логам.
- Раз в месяц: разбор самых частых ошибок (передаются в бэклог), самых шумных источников логов и спорных алертов.

### 10.2. Выбор: OpenSearch (управляемый сервис) и обоснование

**Почему OpenSearch:**
1. **Всё нужное для этого задания «из коробки» и бесплатно:** безопасность по ролям и по полям (критично для политики доступа поддержки), алерты, поиск аномалий (раздел 9), управление сроками (ISM), снимки в S3.
2. **Подходит под нашу команду.** Есть управляемые сервисы, значит, DevOps не обслуживает кластер вручную.
3. **Свободная лицензия.** Нет риска смены условий, как у ELK, и нет цены по объёму, как у Splunk.
4. **Хороший поиск по тексту и полям**, который нужен поддержке («найти всё по номеру заказа», «найти все ошибки расчёта»).

**Плюсы выбора:** бесплатные алерты и аномалии, права на уровне полей, управляемый сервис, привычный язык запросов и большое сообщество.

**Минусы и риски:**
- Тяжелее и дороже по ресурсам, чем Loki (индексируется всё содержимое); при росте объёма нужно следить за размером (раздел 8).
- Нужно настроить шаблоны индексов, права и политики хранения (разовые работы).
- Эксплуатация кластера остаётся (даже управляемого): размеры шардов, обновления.
- Интеграция с Grafana через плагин, а не родная.

**Когда пересмотреть решение:** если объём логов вырастет настолько, что стоимость хранения станет неприемлемой, а поиск по полям будет достаточным, можно перенести тяжёлые низкоценные логи (например, access-логи) в Loki, оставив события заказов, безопасность и ошибки в OpenSearch. Это возможно, потому что формат (JSON с общими полями) и агент (Fluent Bit) остаются теми же.

**Почему не остальные:**
- **ELK** функционально близок, но менялись условия лицензии, а часть безопасности и ML находится в платных уровнях.
- **Loki** отлично дополнил бы Grafana-стек и дёшев, но слабее по алертам, поиску аномалий и безопасности на уровне полей, а нам они нужны сразу.
- **Splunk** мощный, но по цене и зависимости от поставщика не оправдан для компании нашего масштаба.

## 11. Ограничения и риски

- **Дисциплина разработчиков.** Логирование работает, только если все пишут события в едином формате. Решается общей библиотекой, шаблоном и проверкой в CI.
- **Риск попадания персональных данных.** Три рубежа защиты (раздел 7.2) и регулярная проверка индексов.
- **Шум.** Слишком много INFO и алертов делают систему бесполезной. Список INFO ограничен (раздел 2), алерты имеют владельцев и пересматриваются ежемесячно.
- **Нагрузка на серверы.** Агент использует небольшую долю ресурсов; буферизация на диск не должна заполнять диск (ограничение размера буфера).
- **Один DevOps и один C#-разработчик.** Это узкое место внедрения, поэтому волны и привлечение тимлида. Дополнительный довод за найм.
- **Логи не заменяют историю статусов в БД.** Источник истины по заказам остаётся в БД; логи нужны для диагностики и споров.
- **Старые события.** Пока логи не включены, прошлые инциденты восстановить нельзя.
