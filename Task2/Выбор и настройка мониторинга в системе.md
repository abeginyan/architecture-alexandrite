## 2. Мотивация

### 2.1. В чём проблема сейчас

- **Яндекс Метрика показывает только поведение людей на сайте.** Она не видит заказы через API, работу MES, очередь и расчёты. А именно там сейчас теряются заказы.
- **О проблемах мы узнаём от клиентов.** Клиенты жалуются, что заказ делают месяцы вместо трёх недель. Система сама не говорит «заказ застрял».
- **Мы не знаем, где именно узкое место.** Версий много (расчёт цены, очередь, база, ручное подтверждение), но подтвердить или опровергнуть их нечем. Любое улучшение сейчас делается вслепую.
- **Мы уже теряем деньги.** Из-за проблем с заказами компания потеряла несколько крупных контрактов.

### 2.2. Что даст мониторинг компании

| Выгода | Как это проявится |
|--------|-------------------|
| **Раннее обнаружение** | Узнаём о проблеме за минуты, а не по жалобе клиента через недели. Заказ стоит в статусе дольше нормы — приходит алерт |
| **Сохранение клиентов и контрактов** | Можно показать B2B-клиентам прозрачные сроки и статусы. Менеджеры по продажам получают данные, а не оправдания |
| **Правильный выбор, во что вкладывать деньги** | Метрики покажут, что тормозит больше всего: расчёт, очередь или БД. Инициативы из задания 1 будут обоснованы цифрами |
| **Доказательство эффекта** | После каждого улучшения видно, стало ли лучше (например, время расчёта и время ответа дашборда «до» и «после») |
| **Планирование мощности** | Заказов становится на 100 больше каждый месяц. По графикам видно, когда упрёмся в потолок (CPU, соединения БД, очередь) и сколько ресурсов нужно заранее |
| **Защита операторов и их заработка** | Видно, как долго новый заказ доходит до дашборда оператора. Это напрямую влияет на оплату операторов |
| **Обоснование найма** | Данные о нагрузке и ручной работе помогают объяснить бизнесу, зачем нужны второй DevOps или C#-разработчик |
| **Меньше времени на поиск причин** | Вместо многодневного расследования инженер за минуты видит, на каком шаге заказ задержался |

### 2.3. Почему это стоит ресурсов команды (аргументы для бизнеса)

- **Дёшево по сравнению с потерями.** Основные инструменты бесплатные (открытое ПО), основная цена — время 1–2 инженеров на несколько недель. Одного потерянного крупного контракта достаточно, чтобы это окупилось (подставить реальную цифру выручки по потерянным контрактам, она есть у продакта).
- **Не отдельный «проект ради проекта».** Мониторинг — это условие для всех следующих инициатив: нельзя доказать, что очередь или БД стали лучше, если их не измеряли раньше.
- **Можно делать поэтапно.** Первую пользу (алерты на застрявшие заказы и состояние очереди) получим за 2–3 недели, остальное — по мере работы.

### 2.4. Предлагаемые цели (SLO)

Для старта предлагаю договориться с бизнесом о ожиданиях (значения уточнить по реальным данным за 2–4 недели замеров):

- 95% заказов получают рассчитанную цену за ≤ 10 минут для обычных моделей (тяжёлые модели до 30 минут) от момента SUBMITTED.
- Первая страница MES грузится за ≤ 3 секунд у 95% операторов.
- 99% запросов внешнего API отвечают без ошибок 5xx.
- Ни один заказ не «висит» в промежуточном статусе дольше порога (см. раздел 6) без алерта.

## 3. Выбор подхода к мониторингу

Подходы: RED (запросы, ошибки, задержка), USE (использование, насыщение, ошибки) и «Четыре золотых сигнала» (задержка, трафик, ошибки, насыщенность). Кратко: RED подходит для сервисов, на которые приходят запросы; USE — для ресурсов (серверы, диски, базы); золотые сигналы — для самых критичных мест, где нужны все четыре взгляда сразу.

| Часть системы | Подход | Почему |
|---------------|--------|--------|
| Shop API, CRM API | **RED** | Это обычные API: нам важно, сколько запросов, сколько ошибок и как быстро отвечают |
| MES API (в том числе внешний API для клиентов) | **RED** + ярлык «тип клиента» | Нужно отделять запросы внешних клиентов, операторов и внутренних систем |
| **Расчёт цены в MES и очередь RabbitMQ** | **Четыре золотых сигнала** | Самое проблемное место. Нужны все четыре: задержка расчёта, трафик (сколько задач), ошибки (сбои/таймауты) и особенно **насыщенность** (загрузка воркеров и рост очереди) |
| EC2 (серверы), Shop DB, MES db | **USE** | Это ресурсы: смотрим использование, насыщение (очереди, ожидание) и ошибки |
| S3 | **RED** | Скорость и ошибки операций загрузки и чтения |
| Заказы как бизнес-процесс | **Собственные бизнес-метрики** (по статусам) | Ни один из трёх подходов не отвечает на вопрос «где застрял заказ». Это главная метрика для бизнеса |
| Фронтенды (магазин, CRM, MES) | **RED** для запросов из браузера + время загрузки страницы | Основная жалоба операторов — долгая загрузка первой страницы |

**Принципы:**
- Метрики о заказах считаем **по статусам и источнику** (магазин B2C или внешний API), потому что от этого зависит, кому и что чинить.
- В ярлыках **нет** идентификаторов заказа и пользователя (иначе хранилище метрик «взорвётся»). Идентификатор заказа пишем в логи и трассировку, а не в метрики.

Условные обозначения: **Ярлыки** — разрезы метрики (по чему можно фильтровать и группировать). Формат ярлыков намеренно с малым числом значений.

### 4.1. API-сервисы (RED): Shop API, CRM API, MES API

| Метрика | Зачем нужна | Ярлыки |
|---------|-------------|--------|
| **Количество запросов** (`http_requests_total`) | Видеть нагрузку, всплески и реальный рост. Сравнение трафика внешних клиентов и операторов | `service` (shop-api / crm-api / mes-api), `endpoint` (шаблон маршрута, не URL с id), `method`, `consumer_type` (b2c / seller / operator / api_client), `client_id` (**только** для внешнего API) |
| **Доля ошибок** (из того же счётчика по `status_class`) | Видеть 5xx (наши сбои) и 4xx (ошибки клиентов, например неверный файл или превышение лимита) | те же + `status_class` (2xx / 4xx / 5xx) |
| **Задержка ответа** (`http_request_duration_seconds`, гистограмма; смотрим p50, p95, p99) | Среднее скрывает проблемы. p95/p99 показывают, как плохо реально бывает. Основа для SLO | `service`, `endpoint`, `method`, `consumer_type` |
| **Число запросов в обработке** (`http_requests_in_flight`) | Ранний признак перегрузки: запросы копятся | `service`, `instance` |

Почему `client_id` только у внешнего API: клиентов немного, и это нужно, чтобы понимать, кто создаёт нагрузку или получает ошибки. В остальных местах такой ярлык создал бы лишнюю нагрузку на хранилище.

### 4.2. Расчёт цены (золотые сигналы)

| Метрика | Зачем нужна | Ярлыки |
|---------|-------------|--------|
| **Время расчёта цены** (`price_calculation_duration_seconds`, гистограмма) | Задержка в чистом виде. Без неё нельзя понять, тормозит расчёт или очередь перед ним. Сейчас: 2–3 минуты в среднем, до 30 минут | `size_bucket` (small / medium / large по числу полигонов), `source` (b2c / api), `result` (ok / error / timeout) |
| **Количество расчётов** (`price_calculation_total`) | Трафик: сколько заказов приходит на расчёт, как растёт | `size_bucket`, `source`, `result` |
| **Размер модели** (`model_polygons`, гистограмма) | Помогает понять, какие модели тяжёлые, и подобрать границы очередей «лёгкая/тяжёлая» | `source` |
| **Загрузка воркеров расчёта** (`calc_workers_busy` / `calc_workers_total`) | **Насыщенность**: если все воркеры заняты, новые заказы ждут | `instance` |
| **Ошибки и таймауты расчёта** (из `price_calculation_total`) | Показывают заказы, которые «молча» не получили цену | `result`, `size_bucket`, `source` |

> Пока расчёт сидит внутри MES API, эти метрики добавляются в его код. После выноса расчёта в отдельный сервис (И-3) метрики переедут вместе с ним.

### 4.3. Очередь RabbitMQ (золотые сигналы)

| Метрика | Зачем нужна | Ярлыки |
|---------|-------------|--------|
| **Глубина очереди** (`rabbitmq_queue_messages_ready`) | Главный признак насыщения: сообщения копятся быстрее, чем обрабатываются | `queue`, `vhost` |
| **Сообщения без подтверждения** (`messages_unacked`) | Показывает «зависшие» в обработке сообщения | `queue` |
| **Возраст самого старого сообщения** (`oldest_message_age_seconds`) | Лучше глубины показывает «сколько заказ реально ждёт». 100 свежих сообщений — не проблема, одно сообщение возрастом 40 минут — проблема | `queue` |
| **Скорость публикации и скорость обработки** (`publish_rate`, `consume_rate`) | Если публикуем больше, чем обрабатываем, очередь будет расти. Помогает прогнозировать | `queue` |
| **Число потребителей** (`consumers`) | Если 0 — никто не читает очередь, заказы стоят | `queue` |
| **Количество сообщений в DLQ** (очередь «мёртвых» сообщений) | Каждое такое сообщение — потенциально потерянный заказ. Цель — всегда 0 | `queue`, `reason` (error / expired / rejected) |
| **Повторные попытки** (`message_retries_total`) | Рост числа ретраев — ранний признак проблемы в получателе | `topic`, `consumer` |
| **Ошибки обработки** (`message_processing_total` с `result`) | Видно, какие типы сообщений падают | `topic`, `consumer`, `result` (ok / error / retry) |
| **Состояние брокера** (память, место на диске, алармы) | RabbitMQ — единственная точка отказа в интеграции CRM ↔ MES | `node` |

### 4.4. Бизнес-метрики по заказам (самое важное для бизнеса)

| Метрика | Зачем нужна | Ярлыки |
|---------|-------------|--------|
| **Число заказов по статусам** (`orders_by_status`, gauge) | Видно «воронку»: сколько заказов в каждом статусе (INITIATED … CLOSED) и где копятся | `status`, `source` (b2c / api) |
| **Возраст самого старого заказа в статусе** (`order_oldest_age_seconds`) | Прямой ответ на «где застрял заказ». Основа алертов на зависшие заказы | `status`, `source` |
| **Время пребывания заказа в статусе** (`order_status_duration_seconds`, гистограмма) | Показывает, какой переход занимает больше всего времени: расчёт цены, подтверждение продавцом, производство, упаковка, доставка | `from_status`, `to_status`, `source` |
| **Новые заказы** (`orders_created_total`) | Реальная скорость роста, сравнение B2C и API. Сверка с планом +100 заказов в месяц | `source`, `client_id` (для API) |
| **Заказы старше порога** (`orders_stuck_total`) | Простой счётчик «сколько заказов нарушают срок». Быстро читается бизнесом | `status`, `source` |
| **Общее время «от SUBMITTED до PRICE_CALCULATED»** | Ключевой показатель для SLO и для клиентов API | `source`, `size_bucket` |
| **Подтверждения продавцами в ожидании** (заказы в PRICE_CALCULATED, ждущие MANUFACTURING_APPROVED) | Проверяет гипотезу, что часть задержек из-за ручного подтверждения в CRM | `source` |
| **Расхождения между Shop DB и MES db** (`order_status_mismatch_total`) | Данные заказа лежат в двух базах. Периодическая сверка находит потерянные или опоздавшие сообщения | `status_pair` (например, MES=PRICE_CALCULATED / Shop=SUBMITTED) |
| **Сквозное время жизни заказа** (от INITIATED до CLOSED) | Итоговый показатель для бизнеса: «обещали 3 недели — фактически?» | `source` |

### 4.5. Дашборд операторов MES

| Метрика | Зачем нужна | Ярлыки |
|---------|-------------|--------|
| **Время загрузки первой страницы MES** (замер в браузере, `page_load_seconds`) | Основная жалоба операторов. Метрика сервера не покажет, сколько ждёт человек | `page` (dashboard), `status_filter` |
| **Время ответа запроса списка заказов** (`GET /orders`, из RED) | Отделяет проблему «бэкенд» от проблемы «фронтенд» | `endpoint`, `status_filter` |

| **Конфликты при взятии заказа** (`order_assign_total` с `result`) | Показывает, как часто два оператора пытаются взять один заказ | `result` (ok / conflict) |

## 5. Инструменты и принцип сбора (общий выбор)

| Задача | Предложение | Почему |
|--------|-------------|--------|
| Хранилище метрик | **Prometheus** (с длительным хранением, например VictoriaMetrics, если понадобится) | Бесплатно, стандарт индустрии, подходит под Java и C# |
| Дашборды | **Grafana** | Гибкие дашборды отдельно для инженеров, операторов, бизнеса |
| Алерты | **Alertmanager** → чат команды, тикеты, e-mail/звонок | Гибкая маршрутизация по серьёзности |
| Метрики приложений | Java: Micrometer + Spring Boot Actuator; C#: OpenTelemetry / prometheus-net | Минимум кода: часть метрик включается конфигурацией |
| Метрики серверов | node_exporter на EC2 | Стандартный набор |
| Метрики PostgreSQL | postgres_exporter и/или метрики Yandex Monitoring (managed-сервис) | Базы уже управляются Yandex Cloud |
| Метрики RabbitMQ | встроенный плагин Prometheus | Готовые метрики очередей |
| Логи | Централизованный сбор (например Loki или ELK), **JSON-формат** с `order_id`, `trace_id`, `source` | Поиск по заказу по всем сервисам |
| Трассировка | OpenTelemetry + Tempo или Jaeger | Видно, где именно «потерялся» заказ по цепочке Shop → MES → очередь → CRM |
| Фронтенд | Сохранить Яндекс Метрику (поведение пользователей) + замеры скорости и ошибок в браузере | Метрика остаётся для бизнеса, дополняем технической стороной |

## 7. Дополнительное задание: насыщенность и пороги

### 7.1. Почему выбираем именно такие показатели

Насыщенность показывает, **насколько близко ресурс к пределу**, ещё до того, как начнутся ошибки. Заказов становится на 100 больше каждый месяц, поэтому нам важно видеть приближение к пределу заранее. Выбраны показатели, где предел реально проявляется:

- **Загрузка воркеров расчёта и возраст сообщения в очереди** — потому что расчёт до 30 минут: если воркеры заняты, заказы ждут, и это первая причина просрочек.
- **Соединения БД** — у каждой базы один инстанс; исчерпание соединений останавливает приложение.
- **CPU и память серверов** — расчёт цены тяжёлый, а серверы без запаса (по одному экземпляру).
- **Диск** — сломает приложение или БД без шанса на быстрое исправление.
- **Возраст заказа в статусе** — это насыщенность всего бизнес-процесса, а не одного сервиса.

> Пороги ниже — стартовые. Через 2–4 недели замеров их надо пересмотреть по реальным данным, иначе будет много ложных тревог или, наоборот, тишина.

### 7.2. Пороги и реакция

Уровни реакции:
- **L1** — отметка на дашборде, действий не требуется.
- **L2** — сообщение в чат команды + тикет в трекере.
- **L3** — срочное оповещение дежурному (звонок/пейджер) + письмо в поддержку и продакту, если это затрагивает клиентов.
- **A** — автоматическое действие (масштабирование и т.п.), работает после инициативы И-4 (несколько экземпляров).

| Показатель | Предупреждение (L2) | Критично (L3) | Почему такой порог | Что делаем |
|------------|--------------------|---------------|--------------------|-----------|
| **CPU сервера** | > 70% дольше 10 мин | > 85% дольше 5 мин | Запас на всплеск. Расчёт цены даёт долгую нагрузку, а не кратковременную | L2: тикет на анализ. L3: добавить экземпляр (A) или вручную перераспределить нагрузку |
| **Память сервера** | > 80% или swap > 0 дольше 10 мин | > 90% | Нехватка памяти приводит к падению процессов | L2: тикет. L3: перезапуск/добавление ресурсов |
| **Диск** | > 75% или заполнится за < 3 суток | > 90% или заполнится за < 12 часов | Чистка и расширение требуют времени | L2: тикет. L3: срочное расширение, очистка логов |
| **Соединения БД** | > 70% от лимита | > 90% | Исчерпание соединений = полная остановка приложений | L2: проверить утечки и пул соединений. L3: срочно, возможно, увеличить лимит и перезапустить приложение |
| **Медленные запросы БД** | p95 запроса > 1 с дольше 10 мин | p95 > 3 с или рост блокировок | Прямо влияет на дашборд и API | L2: тикет на оптимизацию. L3: найти и остановить тяжёлый запрос |
| **Лаг реплики БД** (после появления) | > 5 с | > 30 с | Дашборд покажет устаревшие данные | L2: тикет. L3: временно читать из основной БД |
| **Возраст самого старого сообщения в очереди расчёта** | > 10 мин | > 30 мин | Расчёт сам занимает до 30 минут, ожидание сверх этого уже просрочка | L2: проверить воркеров. L3: добавить воркеров (A), оповестить продакта |
| **Рост глубины очереди** | Растёт 15 минут подряд | Растёт 30 минут подряд и воркеры загружены > 90% | Показывает, что обработка не успевает за потоком | L2: тикет. L3: масштабирование воркеров (A) или временное ограничение внешнего API |
| **Загрузка воркеров расчёта** | > 80% дольше 10 мин | 100% дольше 5 мин при растущей очереди | Нет запаса — любой всплеск превращается в задержку | L2: тикет на планирование мощности. L3: добавить воркеров (A) |
| **Сообщения в DLQ** | > 0 | > 10 или растёт | Каждое сообщение — потенциально потерянный заказ | L2: тикет сразу при первом. L3: разбор немедленно, сообщение клиентам при необходимости |
| **Число потребителей очереди** | — | = 0 дольше 2 мин | Никто не читает очередь — заказы встали | L3: перезапуск потребителя, оповещение |
| **Заказ в SUBMITTED без цены** | > 30 мин (для обычных моделей) | > 2 часа | Расчёт должен занимать 2–30 мин. Дольше — заказ потерян или завис | L2: тикет, проверка заказа. L3: ручная перезапуск расчёта, письмо поддержке для связи с клиентом API |
| **Заказ в PRICE_CALCULATED без подтверждения продавцом** | > 1 рабочий день | > 3 рабочих дня | Проверка гипотезы о ручном подтверждении | L2: напоминание продавцу. L3: эскалация продакту |
| **Расхождения Shop DB и MES db** | > 0 дольше 15 мин | > 10 заказов | Означает потерянные или опоздавшие сообщения | L2: тикет. L3: запуск сверки и исправление |
| **Доля ошибок 5xx API** | > 1% за 5 мин | > 5% за 5 мин | Влияет на заказы клиентов и репутацию | L2: тикет. L3: срочный разбор, при необходимости откат релиза |
| **Задержка API (p95)** | Выше цели SLO на 20% | Выше цели SLO вдвое | Клиенты API и B2C замечают замедление | L2: тикет. L3: анализ нагрузки, ограничение «шумного» клиента |
| **Время загрузки первой страницы MES (p95)** | > 3 с | > 5 с | Операторы теряют время и деньги | L2: тикет. L3: срочный разбор (расчёты, БД) |

### 7.3. Ограничения и честные замечания

- **Автомасштабирование (A)** заработает только после инициативы про несколько экземпляров (И-4) и выноса расчёта в отдельный сервис (И-3). До этого на L3 реакция остаётся ручной.
- **Дежурство.** У нас один DevOps. Звонки по ночам на одного человека — не вариант: нужен график дежурств (минимум два человека, например DevOps + бэкенд-разработчик с обучением). Предлагаю на старте ограничиться рабочими часами и срочными оповещениями только для критичных алертов (пропажа очереди, рост DLQ, падение API). Это дополнительный аргумент за найм второго DevOps/SRE.
- **Борьба с шумом.** Если алертов слишком много, команда перестанет реагировать. Каждый алерт должен иметь описание в runbook и владельца. Алерты, которые срабатывают впустую, пересматриваем на ежемесячном разборе.
- **Взаимосвязь с бизнесом.** Метрики «заказ завис» должны быть видны продакту и менеджерам по продажам на отдельном дашборде, чтобы они сами могли предупредить клиента, а не ждать звонка.
